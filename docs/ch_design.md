# Contraction Hierarchies (CH) 導入設計 (2026-11-11、Claude)

目的: 3 県チェーン 11 秒・同県 40km 約 1.1 秒の経路探索を、桁違いに速くする。全国対応 (47 県) でも 4 県以上のチェーンが遅くならないようにする。
決定: 双方向 A* ではなく CH を採用 (ユーザー決定 2026-11-11)。

## 1. 方針 (おすすめ 1 つ)

- **対象は「自転車・おすすめ (BICYCLE × RECOMMENDED)」だけ**。コストは `距離 × 倍率(道路種別, 勾配, 好み, モード)` で好みごとに変わるため、CH は 1 つの固定コストにしか使えない。平坦優先・坂道優先・徒歩・車は **従来の A\*** のまま (CH が無い県・ファイルが壊れた場合も A\* に戻す)。
- **前処理はオフライン** (Mac。`:osm-importer` か `:routing-core` のツール)。端末では作らない。
- **既存の `.graph` / `.graph.idx` は変更しない**。CH は別ファイル `<name>.graph.ch` (サイドカー) に置く。ヘッダにノード数・辺数・`.graph` の識別 (サイズ+先頭/末尾のハッシュ) を持たせ、不一致なら使わない。
- **ノード単位の CH (ターンコスト無し)**。現行 A\* がターンコストを持たない前提 (Codex が確認して報告する)。持つなら範囲を再検討。
- 結果の **コストは A\* と一致**すること (A\* の下限 0.90 は許容的なので A\* も最適)。同コストの別経路は許容、コスト差は許容しない。
- ショートカットは「中間ノード」を持ち、経路展開で **元のノード列** に戻す (案内・勾配・標高は今のまま `nodeIndices` から作る)。距離 (m) も辺ごとに持つ。

| S2 | `.graph.ch` 形式 (mmap 読み込み) と、同県探索への組み込み (CH があれば使い、無ければ A\*) | `:routing-core`, `:app` (`RealRoutePlanner`) | 全テスト + 実機で結果同一 |

## 3. S1 の数値基準 (go / no-go)

開発は Tottori (最小) → Hiroshima (最大) で行う。
- 突き合わせ: 同県のランダム 1000 組 (最近傍ノード) で、A\* とコスト一致 (相対誤差 1e-9 以内、到達可否も一致)。
- 速度: Hiroshima の 40km 級で、問い合わせが **100 ms 以下** (JVM、ウォーム)。A\* の現状 (約 1 秒) と並べて報告。
- サイズ: `.graph.ch` が **`.graph` の 1.0 倍以下** (ショートカット込み)。超えたら要相談。
- 前処理時間: 1 県 **2 時間以内** (`-Xmx6g`)。メモリが足りなければ報告。
- 通らなければ no-go とし、理由を報告して止める (双方向 A\* に切り替える判断は Claude/ユーザー)。

## 4. S1 の設計メモ (Codex への指示の背景)

1. 入力: `LazyMappedRoadGraph` か `MappedRoadGraph` で読んだ有向グラフ (一方通行を反映)。辺コストは `routingEdgeMultiplier(type, grade, RECOMMENDED, BICYCLE) * distance`。`NaN` の倍率 (通れない道) は辺として入れない。
2. ノード順序: 辺差 (edge difference) + 削除済み隣接数 + 階層の深さ、遅延更新つき優先度キュー。前処理は 1 スレッドで先に動かし、速度が足りなければ並列化を検討。
3. 縮約: ノード v を縮約するとき、(u→v, v→w) ごとに、v を除いた witness 探索 (settled 上限・コスト上限つき) で `cost(u→v)+cost(v→w)` より短い道が無ければショートカット u→w (中間 = v) を追加。witness 探索の打ち切りでショートカットが増えるのは許容 (正しさは保たれる)。
4. 出力: ランク、上向きの前向きグラフ (rank が上がる辺) と上向きの後ろ向きグラフ (逆辺)。各辺: 相手ノード、コスト (double)、距離 (float か double)、中間ノード (-1 = 元の辺)。CSR 配列。
5. 問い合わせ: 双方向ダイクストラを上向きグラフだけで実行 (前向き・後ろ向きを交互)、最小の合計コストの会合ノードを選ぶ。停止条件は両方の最小キーが現在の最良コスト以上。経路は会合ノードから両側を親でたどり、ショートカットを再帰 (スタックを使わない反復) で展開。
6. 検証: 同じ OD で `AStarRouter` (本番の A\*) とコスト・距離・到達可否を比較する JUnit (小さな合成グラフ) と、実グラフのベンチ (`benchmarkRealGraph` と同様の Gradle タスク)。合成グラフのテストには、一方通行・行き止まり・非連結・コスト同値の分岐を含める。
7. 本番コードの変更は最小: 追加ファイル中心 (`ContractionHierarchy.kt` 等)。既存の `LazyMappedRouting.kt` は、辺を列挙する読み取り API を足す程度にとどめる。

## 5. リスク

- 前処理の時間・メモリ (Hiroshima は 2 億バイト級のグラフ)。
- 勾配 (`grade`) が辺ごとに入るので、辺の総数が多く、ショートカットが増えやすい。
- 県またぎは通り口で分割した県ごとの CH で足りる設計 (S3 で検証)。足りなければ、通り口ノードを最上位ランクに固定する方式を検討。
- 好みを CH に入れないため、「平坦優先」の経路は遅いまま。必要なら好みごとの CH (ファイルが 3 倍) を別途判断。

## 6. S3 結果 (2026-11-11、実機 Galaxy S26、山口→広島→岡山)

- 県またぎは `routeAcrossChainCh` (`CrossChainChRouting.kt`)。各県の CH で「始点→通り口」「通り口→通り口」「通り口→終点」を `searchMany` (前向き多始点 + RPHAST 掃引) で一括計算し、復元は各県で `ch.route` を 1 回ずつ。おすすめ×自転車のときだけ使い、CH が無ければ A* に戻る。
- 結果は A* と同一 (JVM で全 OD コスト一致、実機で距離・コスト・経路ハッシュ一致)。
- 3 県: 10.2 秒 → 約 3.0〜3.5 秒、2 県: 3.4 → 2.1 秒。内訳の大きかったもの: 通り口ごとの後ろ向き探索 (1.4 秒) → RPHAST で 0.04 秒、CH の距離計算が全辺の種別表を作っていた (1.3 秒) → 辺ごとに引く `lazyTypes` で 0.02 秒、チェーン用グラフが標高/道路名/車線の表を読んでいた (約 0.8 秒) → `readRichSections=false`。
- 試して効かなかった/不可: 復元時の GC 除去 (効果なし)、最後の中間県を開いたままにする (OOM)、バックグラウンド先読み (効果は未確認)。
- 残り: 通り口の照合 約 0.6 秒、案内用に各県をもう一度開く 約 0.7 秒。通り口を事前計算してファイル化すれば前者は消せる (S4 で検討)。

## 7. 通り口の事前計算 (2026-11-11、JVM。実機は未確認)

- 隣り合う 2 県の通り口 (共通 OSM ノード) を `<A>__<B>.portals` に持つ (A, B は graph の基本名、大文字小文字を無視した辞書順)。`routeAcrossChainCh` は、あれば隣県の ID 索引を読まず、現在の県の索引も作らない (その後の GC も省く)。A\* のチェーン (`routeAcrossChain`) は従来のまま。
- 形式 (ビッグエンディアン、`CrossPortalsFile.kt`): ヘッダ 68 バイト = マジック `CMPT`、バージョン 1、件数 (各 Int)、A の graph の識別、B の graph の識別 (`GraphFingerprint` = size, firstCrc, lastCrc の各 Long)、本体の CRC32 (Long)。本体は `nodeId (Long), aIndex (Int), bIndex (Int)` を `nodeId` 昇順。逆向き (B→A) は読み込み時に A/B の列を入れ替える。
- 使えないとき (無い・切れている・マジック/バージョン違い・CRC 不一致・識別が今の graph と合わない) は null を返し、従来の照合に戻る (例外は投げない)。さらに探索側で、番号の範囲と抜き取り最大 64 件の ID を graph と突き合わせる。a 側が合わなければ従来の照合、b 側 (次の県) が合わなければ ID から番号を引き直す。ログは `CHAIN_PORTALS stage=<i> source=file|match count=<n>`。
- 生成: `./gradlew :routing-core:buildPortals -Pa=<A.graph> -Pb=<B.graph> -Pout=<file>` (または `-Pgraphs=<カンマ区切り> -PoutDir=<dir>` で全組)。パイプラインは `python3 scripts/build_portals.py` (5 県の 10 組を計算し、通り口のある 7 組だけ `packages/` に置く。0 件の 3 組は `packages/portals_empty.json` に控えて次回スキップ)。`refresh_data.py` では昇格の後に実行 (組の両県の graph が確定してから)。`push_data.sh` が `packages/*__*.portals` を転送する。
- 件数とサイズ: 広島–岡山 6,197 件 (99KB)、鳥取–岡山 7,317、島根–広島 5,411、島根–山口 3,575、広島–山口 2,599、鳥取–島根 2,364、鳥取–広島 823。合計 約 450KB。生成は 5 県まとめて約 9 秒、2 回目は約 1 秒 (全スキップ)。
- JVM の前後 (`benchmarkChainCh -Pod=20`、Mac、A\* との不一致はどれも 0):

| 組 | `portal_match` 平均 | CH 全体 平均 (open 込み) |
|---|---|---|
| 山口→広島→岡山、照合 (従来) | 322.7 ms | 1724.6 ms |
| 山口→広島→岡山、通り口ファイル | 4.1 ms | 1266.4 ms |
| 岡山→広島→山口 (逆向き)、通り口ファイル | 4.9 ms | 1350.4 ms |
| 広島→岡山、通り口ファイル | 2.9 ms | 964.4 ms |

- 通り口ファイルありの 4〜5 ms は、2 県ぶんの識別の計算 (先頭/末尾 1MB の CRC) を含む。切れたファイル・別の組のファイルを置くと `stages_from_file=0` になり、照合に戻って不一致 0 のまま (`-Pportals=<壊したフォルダ>` で確認)。
- 残り: 実機での確認 (距離・コスト・経路ハッシュが変わらないこと、`portal_match` の実測)。`.portals` を実機へ転送し、新しい APK を入れてから行う。
