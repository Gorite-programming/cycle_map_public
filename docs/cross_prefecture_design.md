# 県またぎ経路の拡張設計 (経由地つき・3 県以上)

作成: 2026-11-10。前提: `CrossGraphRouting.kt` (2 グラフ・通り口 1 回・経由地なし) が実装済みで、実機で井口 → 新岡山港 (179.6km) が約 4 秒で表示できる。
本書はその拡張の設計。実装は Codex に 2 段階で渡す (C1: routing-core、C2: アプリ)。

## 1. 要件
| # | 要件 | 例 |
|---|---|---|
| R1 | 経由地つきの経路で、区間ごとに県が違ってもよい | 広島駅 → (経由) 岡山駅 → 新岡山港 |
| R2 | 間に別の県をはさむ 3 県以上の経路 | 山口 → (広島を通って) → 岡山 |
| R3 | メモリ: 同時に開くグラフは最大 2 つ (現在のアプリのグラフ + 計算中の一時グラフ 1 つ)。Java ヒープ上限 512MB を守る (県またぎ計算後の実測 約 357MB) | |
| R4 | 通常の (同じ県内の) 経路の速度・結果は変えない | |
| R5 | グラフは結合しない (県ごとの分割を維持) | |
| R6 | 県またぎでは代替ルートを出さない (従来どおり) | |

範囲外: 県境を行き来する経路 (同じ 2 県間を 2 回以上またぐ)、対応外の県 (兵庫・愛媛など) を通る経路、ナビ中の県切替の作り込み (現状の自動切替で足りている)。

## 2. 基本方針: 区間 (leg) に分けて、区間ごとに解く
経路 = 停止点の列 `s0, w1, …, wn, g` を、隣り合う 2 点の「区間」に分ける。区間ごとに:

| 区間の始点・終点の県 | 解き方 |
|---|---|
| 同じ県 | その県のグラフで `routeWithSnapFallback` (既存。県が現在のグラフと違えば一時グラフを開く) |
| 隣り合う 2 県 | 既存の `routeAcrossGraphs` (通り口 1 回) |
| 3 県以上 (間にはさむ県がある) | 新規の `routeAcrossChain` (本書 §3) |
| 判定できない/対応外/グラフ無し | 従来のフォールバック (出発県内で届く所まで + 「未対応」の警告) |

- 区間は独立に最適化する (経由地を必ず通る、という条件上、区間ごとの最適の連結が全体の最適)。
- 区間をつなぐときは、経由地ノードの重複を 1 つにする。
- 一時グラフは区間の計算が終わったら `close()`。**同時に開くのは「現在のアプリのグラフ + 計算中の一時グラフ」まで**。
  3 県チェーンの中間グラフ (例: 山口 → 広島 → 岡山 の広島) も、1 つずつ開いて閉じる (§3 の再構成のときは開き直す)。

## 3. 県のチェーン探索 (`routeAcrossChain`)
グラフ列 `G0, G1, …, Gk` (k ≥ 2)。`Gi` と `Gi+1` の間に通り口集合 `Pi` (共通 OSM ノード ID)。

1. **G0**: 始点から `P0` の全通り口までの最小コストを求める (既存の `routeToPortals`、ダイクストラ)。
2. **中間 Gi (1 ≤ i ≤ k-1)**: 入口 = `Pi-1` の通り口 (初期コスト = 前段の値)、出口 = `Pi` の通り口。
   複数始点のダイクストラで、**出口の通り口すべての最小コストを求める**。各出口に「どの入口から来たか (入口の ID)」と、親配列のスナップショットを持たせる。
   - 出口の全通り口が確定するか、到達不能が確定するまで続ける (打ち切りは `maxExpandedNodes`)。
   - 入口の ID ラベルは、ノードごとの `origin` 配列 (IntArray) で伝播させる (コストが下がる辺で親と一緒に更新)。
3. **Gk**: 既存の `routeFromPortals` (複数始点 A*) で終点へ。ヒューリスティックは従来どおり (直線距離 × 0.90)。
4. **再構成** (後ろ向き): Gk の経路の先頭の通り口 → その通り口の `origin` で Gk-1 の入口 → … と G0 まで戻る。各段の部分経路は、その段の親配列スナップショットでたどる。
   部分経路のノード座標・ID・番号を取るにはグラフが要るので、**後ろ向きに 1 つずつグラフを開き直して**取り出す (開き直しは 1 つ 約 0.45 秒)。
   (中間グラフを開いたまま保持する案は、ヒープが増えるので採用しない。実測で余裕があれば最適化してよい。)

結果 `CrossChainResult`: 統合した `nodeIds` / `coordinates` / 距離 / コスト、段ごとの部分 `parts: List<CrossRoutePart>` (各段の `nodeIndices` はその段のグラフの番号)、使った通り口の ID の列、`wasCancelled` / `wasTruncated`。
既存の `CrossRouteResult` (2 グラフ) は互換のため残す。内部で `routeAcrossChain` に統一してもよいが、既存テスト・ベンチの結果を変えないこと。

正確さ: 各隣接県間の通過が 1 回、かつ県の並び (チェーン) が与えられていれば、全体の最適コストと一致する (中間も出口の最小コストを全部求めるため)。
チェーンの選び方による取りこぼし (別のチェーンのほうが安い) は許容し、文書に残す。

## 4. チェーンの決め方 (アプリ側、C2)
- 対応県の隣接表 (静的): 山口-島根、山口-広島、島根-広島、島根-鳥取、広島-岡山、広島-鳥取、岡山-鳥取。
  端末にデータがある県だけを使う。実際の通り口が 0 件の組は、グラフを開いたときに辺を外す (その場でチェーン候補を捨てる)。
- 始点の県から終点の県への最短 (県数が少ない) チェーンを幅優先で求める。同数なら、各県の中心間の直線距離の合計が小さい方。
- 最大 3 本の候補チェーンを、順に試す (最初に到達できたものを採用)。県が 4 つ以上のチェーンは許可するが、計算が長いので「長距離の計算中」の案内を出す (既存の仕組み)。

## 5. 案内・標高の連結 (C2)
- 現状の `mergeInstructionParts` / `mergeElevationParts` は 2 部品用。**N 部品に一般化**する (部品 = そのグラフでの案内/勾配/標高)。区間の連結 (経由地) も同じ関数で扱えるようにする。
- 連結後の `routeIndex` と `distanceFromStartMeters` は全体基準。重複ノードの扱いに注意 (番号のずれ・二重表示が無いこと)。
- 経由地ごとの到着案内: 既存の経由地マーカー・到着判定の仕組みに合わせる (通常の経由地つき経路と同じ表示になること)。
- 標高: 部品ごとに `segmentGradesAlongIndices` / `nodeElevationsAt` を使い、連結。古い結果が残らないこと (既存の `crossRouteElevationState` の仕組みを使う)。

## 6. ナビ中・リルート
- 現状: リルートでも県またぎ探索を使う (経由地なし)。**経由地が残っているリルートも、この拡張で対応する**: 現在地 → 残りの経由地 → 終点を、同じ区間分割で解く。
- ナビ中のグラフ自動切替は既存のまま (位置が県境を越えると切り替わる)。切替直後に走るリルートが、現在のグラフを一時グラフと取り違えないこと (`jobGraph` はロック内で使う)。
- 再計算の繰り返し抑止 (前回の地点から 30m 以内では要求しない) は維持。

## 8. テスト方針
- **同値テスト (C1)**: 小さな合成グラフ (格子) を 1 つの G にして、3 つ (A|B|C の帯) に分割する (隣り合う帯は共通ノード = 通り口を持つ)。
  始点 A、終点 C で `routeAcrossChain` のコスト・距離が G 上の `route()` と一致 (preference 3 種)。通り口が複数ある場合、最適なものが最短の通り口と違うケースを含める。
  一方向の道・勾配付きの辺を含める。通り口なし = 到達不能、キャンセル = `wasCancelled`。
- **実データ (C1)**: 山口・広島・岡山のグラフで、山口 → 岡山の経路が引けること (座標は上の例)。距離・時間・通り口を報告。
  データは `packages/Yamaguchi.zip` などから `work/` に展開 (git 管理外)。graph と idx のみ。
- **アプリ (C2)**: 区間分割・チェーン選択・N 部品の連結は純粋な関数にして JVM で単体テスト。
- **実機 (Claude が行う)**: 3 県・経由地つきの表示、ナビ開始、リルート、メモリ。
